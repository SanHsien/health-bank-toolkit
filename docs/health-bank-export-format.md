# 健保快易通「健康存摺」匯出格式與分析規則

給之後分析健康存摺資料的 AI 看的參考。內容是 2026-10 用一份真實匯出逐項核對過的**格式與判讀規則**，
不含任何個人資料、數值或就醫內容。

解析工具：[`tools/health_bank_parser.py`](../tools/health_bank_parser.py)。
報告提示詞：[`templates/health-report-pdf-prompt.md`](../templates/health-report-pdf-prompt.md)。

---

## 1. 處理原則（先讀）

- **原始檔與解析結果都不得放進任何 git repo。** 放在 repo 外的私人資料夾；解析器的輸出目錄在 git 工作樹內會被拒絕。
- 先跑解析器，AI 只讀脫敏後的 JSON，不要直接讀原始 HTML。
- 脫敏後的資料交給雲端 AI，仍然是把健康資料傳給該服務；使用者要知道這件事。
- 可以對照公認臨床標準解讀數值、給生活與追蹤建議、列出警訊與可以問醫師的問題；不下確定診斷，不建議增減、停用或更換藥物（2026-10-24 起，原本只整理不解讀，使用者要求加入分析與建議）。

```text
匯出 ZIP（有密碼）──使用者自行解壓──▶ 私人資料夾/*.html
        │
        ▼
python tools/health_bank_parser.py <私人資料夾> <私人資料夾>/parsed
        │
        ▼
parsed/summary.json + 各類別 JSON（已脫敏）──▶ AI 整理報告
```

---

## 2. 匯出檔案

- 下載的是**加密 ZIP**，密碼由使用者在健保快易通設定。AI 不要代為輸入密碼；請使用者自行解壓縮。解析器遇到加密 ZIP 會直接拒絕並提示先解壓。
- 解壓後是一個類別一個 HTML，檔名為 `<類別>_<民國年月日>.html`（例如 `檢驗檢查結果_1151023.html`），另附兩張 GIF（頁面圖示，可忽略）。
- 已知 11 類：門診資料、住診資料、用藥資料、手術資料、牙醫門診資料、檢驗檢查結果、影像或病理檢查資料、預防接種資料、COVID-19疫苗接種／病毒檢測結果、器捐或安寧緩和醫療意願、糖尿病追蹤。
- **編碼不一致**：大多是 UTF-8，但「COVID-19疫苗接種／病毒檢測結果」是 Big5（cp950）。以 UTF-8 寬鬆讀取會變亂碼，要先判斷編碼。

## 3. 每個 HTML 的結構

每檔大約 3 張表：

| 順序 | 內容 | 處理 |
|---|---|---|
| 1 | 標題表（含姓名等個資） | 整張丟棄 |
| 2 | 資料表（真正的資料） | 解析 |
| 3 | 「註：」說明表 | 丟棄 |

資料表的陷阱：

- **大量整列空白的間隔列**：欄數和主檔相同，但每格都是空的（門診一份就有上百列）。用「列數」估就醫次數會高估很多，要先濾掉全空白列。
- **單格列**：只有一個儲存格的分隔列。
- **主檔／明細兩層**：一次就醫是一列主檔，底下接一段明細（醫囑或藥品），明細前常有一列子表頭。
- **主檔欄數會少 1～2 格**：部分主檔列少了前面的格子（原表用合併儲存格），欄位要重新對齊，不能直接照位置讀。
- **健保卡就醫序號會重複**：同一號碼出現在不同次就醫，不能拿來當唯一識別；它也屬可追溯個人的資料，一律遮蔽。

## 4. 各類別表頭

主檔表頭（第一列）與明細子表頭：

| 類別 | 主檔表頭 | 明細子表頭 |
|---|---|---|
| 門診資料 | 健保署服務單位、醫事機構、就醫日期、交付調劑、檢查或復健治療日期、健保卡就醫序號、主診斷碼、主診斷名稱、主處置碼、主處置名稱、部分負擔金額、健保支付點數 | 醫囑代碼、醫囑名稱、醫囑總量 |
| 用藥資料 | 健保署服務單位、醫事機構、就醫(調劑)/入院日期、出院日期、申報起日、申報迄日、健保卡就醫序號、疾病分類碼、疾病分類名稱 | 藥品醫囑代碼、藥品名稱、藥品藥理分類、給藥日數、執行起日、執行迄日、醫囑總量 |
| 住診資料 | 健保署服務單位、醫事機構、入院日期、出院日期、申報起日、申報迄日、健保卡就醫序號、疾病分類碼、疾病分類名稱、處置碼、處置名稱、部分負擔金額、健保支付點數 | 醫囑序號、執行起日、執行迄日、醫囑代碼、醫囑名稱、醫囑數量 |
| 手術資料 | 同住診資料，第三欄為「就醫日期/入院日期」 | 同住診 |
| 牙醫門診資料 | 健保署服務單位、醫事機構、就醫日期、健保卡就醫序號、主診斷碼、主診斷名稱、主處置碼、主處置名稱、部分負擔金額、健保支付點數 | （少見） |
| 檢驗檢查結果 | 健保署服務單位、醫事機構、就醫日期/入院日期、檢驗(查)日期、資料上傳時間、醫囑代碼、醫囑名稱、檢驗項目名稱、結果值、單位、參考值 | 無（單層） |
| 預防接種資料 | 接種日期、疫苗中文名稱、醫事機構名稱 | 無 |
| 影像或病理檢查資料 | 影像或病理報告內容（自由文字） | 無 |
| 器捐或安寧緩和醫療意願 | 健保卡註記日期 等 | 無 |

辨識類別要看**表頭欄位組合**，不要只看檔名：例如住診與手術表頭幾乎相同，差在第三欄名稱。

## 5. 日期

- 一律是**民國年**：`112/10/12` = 2023-10-12（民國年 + 1911）。部分欄位帶時間。
- 解析器保留原值，另加 `<欄位>_iso`。分析時用 ISO 欄位排序與畫時間軸。

## 6. 檢驗結果的判讀

- **原始資料沒有「判定」欄**，不能把沒有標記的結果當成正常。
- 參考值格式是 `[下限][上限]`：
  - `[3.5][5.5]`：數值範圍，可比對。
  - `[][130]`、`[40][]`：單邊範圍，可比對。
  - `[N][N]`、`[無參考值][]`、`[neg -][neg -]`、`[無][]`、`[－][＋/－]`、`[Negative][]`：文字型，無法用數字比對。
- 判定規則（解析器的 `flag` 欄）：數值與所有出現的界限都是數字時，才判 `偏高`／`偏低`／`正常`（含邊界值算正常）；其他一律 `未判定`。
- 「未判定」不代表異常，只代表無法自動比對；文字型結果（如陰性／陽性）要照原文呈現。
- 同一項目在不同醫院可能用不同名稱（例如只有英文、或中英文並列），參考值也可能略有差異。畫趨勢時以**同一項目名稱＋同一單位**為一條線，並標註參考值是否變動。
- 參考值由各醫院提供，不同醫院可能不同；比對時以該筆紀錄自己的參考值為準。

## 7. 脫敏欄位

| 一律遮蔽 | 保留（分析需要） |
|---|---|
| 姓名、身分證字號、出生日期、電話、地址、病歷號、健保卡就醫序號、標題表整張 | 醫事機構名稱、診斷碼與名稱、處置、藥品名稱與藥理分類、檢驗項目與數值、日期 |

影像或病理報告是自由文字，可能夾帶個資，已經過文字脫敏；呈現時仍以摘要為主，不要整段貼出。

## 8. 解析後的 JSON

`summary.json`：各類別筆數（`counts`）、明細筆數（`detail_counts`）、日期範圍（`date_ranges`）、解析診斷（`diagnostics`）、各檔編碼（`files`）、解析器版本（`parser_version`）。

**先看 `parser_version` 與 `diagnostics`**：
- `parser_version` 小於 3 的輸出有第 9 節的對齊問題，要照該節自己補救，或用新版解析器重跑。
- `short_master_rows`（欄位推斷對齊的主檔）、`unmatched_rows`、`orphan_detail_rows` 數量很大時，代表格式和本文件描述不同，結果要保留疑問。
- `secondary_rows`：併回主檔的次診斷／次處置列數；`duplicate_rows`：去掉的重複上傳筆數。

類別 JSON 的主要欄位：

- `labs`：`test_date(_iso)`、`institution`、`order_name`、`item`、`value`（數字或文字）、`value_raw`、`unit`、`reference`、`ref_low`、`ref_high`、`flag`。
- `outpatient`：`visit_date(_iso)`、`service_date(_iso)`、`institution`、`diagnosis_code`、`diagnosis_name`、`procedure_name`、`copay`、`points`、`secondary_diagnoses[]`、`secondary_procedures[]`（各為 `code`、`name`）、`orders[]`。少數主檔的 `visit_date` 空白、只有 `service_date`（交付調劑、檢查或復健治療日期），是真的就醫紀錄，排時間時改用 `service_date`。
- `medications`：`visit_date(_iso)`、`institution`、`diagnosis_name`、`drugs[]`（`drug_name`、`drug_class`、`days`、`start_date`、`end_date`、`quantity`）。
- `inpatient` / `surgery`：入院（就醫）與出院日期、診斷、處置、`secondary_diagnoses[]`、`secondary_procedures[]`、`orders[]`。手術的 `orders` 欄位是 `surgery_date`、`order_code`、`order_name`、`body_site`（診療部位）、`quantity`。
- `dental`：同門診，`orders` 另有 `tooth_code`、`tooth_name`（牙位）。
- `imaging_reports`：`institution`、`visit_date`、`test_date`（檢查日）、`uploaded_at`、`order_code`、`order_name`、`report`（內文）。
- `vaccinations`、`directives`、`generic`（未知表格，保留表頭與列）。

## 9. 解析結果的已知陷阱（2026-10-24 用真實匯出核對）

parser v2 的筆數是「資料列數」，不等於就醫次數。**parser v3 已在解析時處理下表的問題**；拿到 v2 的舊輸出時，要照「v2 輸出的補救」一欄自己處理，否則次數、排名、趨勢都會錯。

根本原因：門診、住診、牙醫的主檔表頭第一格跨好幾列（rowspan），底下接「次診斷碼N／次診斷名稱N」「次處置碼N／次處置名稱N」子表頭列；資料裡每一筆主檔後面**固定**跟著同樣數量的次要列（例如門診 2 列、住診 8 列），順序與子表頭相同，沒有資料時整列空白（就是第 3 節說的「大量整列空白的間隔列」）。v2 先丟掉空白列，就分不出剩下的列是次診斷還是次處置，於是當成新的一筆主檔。v3 保留空白列的位置來對應子表頭。

| 類別 | 現象（v2） | v3 | v2 輸出的補救 |
|---|---|---|---|
| `outpatient`／`inpatient`／`dental` | 次診斷／次處置列被解析成獨立一筆：沒有日期、`service_unit` 空白，代碼與名稱錯位到 `institution`、`visit_date` 等欄，醫囑 `orders` 掛在這一列；次診斷名稱有時落在 `card_seq` 欄被遮蔽 | 併回所屬主檔的 `secondary_diagnoses`／`secondary_procedures` | 併回前一筆主檔，不另算就醫；診斷排名只用主診斷 |
| `outpatient`／`inpatient`／`dental` | `service_unit` 為「次診斷碼N」「次處置碼N」的列是子表頭，被當成欄位短少的主檔 | 當成子表頭讀取 | 丟棄 |
| `surgery` | 明細子表頭（手術日期、醫囑代碼、醫囑名稱、診療部位、醫囑數量）不認得，明細欄位錯位：`end_date` 放醫囑代碼、`order_code` 放醫囑名稱 | 認得子表頭，欄位正確 | 照錯位後的位置取值 |
| `dental` | 明細子表頭（含牙位代碼、牙位名稱）不認得，明細進 `extra_rows` | 進 `orders` | 從 `extra_rows` 讀 |
| `imaging_reports` | 表頭兩列（檢查資訊列＋「影像或病理報告內容」），只認得第二列：資料的資訊列 `report` 是服務單位、`extra.overflow` 是其餘欄位，下一列 `report` 才是內文 | 兩列配對成一筆 | 兩列配對 |
| `imaging_reports` | 同一份報告常上傳兩次，空白與全形斜線可能不同 | 以檢查日＋醫囑代碼＋內文（去掉空白標點）去重 | 同左 |
| `labs` | 同一結果常重新上傳（只差上傳時間，偶爾掛在兩個醫囑下） | 以檢驗日＋醫院＋項目＋單位＋原始數值去重 | 同左；重複比例可能很高 |
| `labs` | 參考值 `[0][0]`（凝血檢查的對照值等）被判成 `偏高` | 判為 `未判定` | 改判 `未判定` |
| `vaccinations` | 「預防接種」與「COVID-19」兩個檔案重複列出同一劑 | 以日期＋疫苗名稱＋機構去重 | 同左 |
| 全部 | 藥品／醫囑代碼中「0 開頭的長數字」被當成電話遮蔽（例如 `AC[PHONE_REDACTED]`） | 前面緊接英數字時不當電話 | 代碼不可用，只用名稱 |
| `directives` | 註記日期可能空白 | 不變（資料本身空白） | 寫「有註記、日期資料不足」 |

影像報告內文可能含年齡、醫師姓名等可識別資訊，摘要時不要帶出。
